# RecoverIA Phase 4.6B.5B-B2-B2 — Real pilot wiring

## Status

Production-shaped wiring is implemented and validated offline as the final code baseline before isolated synthetic infrastructure activation. It remains inactive. No cloud resource, database, OAuth flow, Google endpoint, Drive corpus, Client Zero data, or deployment was accessed.

## Real execution path

The single pilot path is `RealGoogleDriveClient` → `RealGoogleDrivePilotRuntimeDriver` → `OneShotGoogleDrivePilotOrchestrator` → `IncrementalCorpusProcessor` with the configured `DocumentUnderstandingProvider` → `DurableCheckpointPort.save` CAS → terminal execution success. There is no alternate parser, source, or checkpoint path.

The driver is fixed to one organization/connection client and one authorized root. It rejects arbitrary roots and Shared Drive configuration. Native Google documents, shortcuts, and non-PDF records are not downloaded.

## Retry ownership

The orchestrator is the only retry owner. Every eligible transport declares a symbol-keyed retry mode. `SingleAttemptSignalBindingTransport` fails during construction unless its delegate explicitly declares `SINGLE_ATTEMPT`; `RetryingGoogleDriveTransport` and any alternative declaring `RETRY_CAPABLE` are rejected before a request. The binding delegates each client operation once and only injects the orchestration `AbortSignal`. With `maximumRetryAttempts = 3`, the lowest boundary observes exactly three calls for two retryable failures followed by success, three for persistent retryable failure, and one for terminal authorization failure. Nested N×N retry amplification is structurally blocked.

## Root proof and bounded download

Discovery uses the existing `RealGoogleDriveClient` authoritative ID/parent-chain proof. Every PDF download calls the same client's `readPdfContent`, which re-fetches and re-proves the complete ancestry immediately before the content request. Moving the file or an ancestor outside the root, trashing either, losing permission, or entering the wrong Drive context fails closed before content download.

The existing bounded HTTP transport enforces `maximumPdfBytes` while consuming the response stream and aborts the reader when the bound is exceeded. Driver and orchestrator byte checks remain defense in depth.

## Audit ordering

The orchestrator durably appends a redacted `STARTED` security event before invoking `driver.download`. If audit append fails, the download is never called. `SUCCEEDED` or `FAILED` audit follows the bounded download. Audit identifiers are hashes, not raw file IDs or filenames.

## Corpus processing and checkpoint safe commit

Only content downloaded through the audited orchestrator path is exposed through a cache-backed `DocumentSource`. `IncrementalCorpusProcessor` remains the sole corpus path, preserving normalization, duplicate detection, identity clustering, relationships, provenance, and FACT/INFERENCE/UNKNOWN semantics.

The terminal order is:

1. authoritative discovery and pagination complete;
2. every required audited PDF download completes;
3. existing corpus processing completes without failures;
4. deadline and abort state are rechecked before entering the durability commit;
5. checkpoint is saved with the previously loaded version as CAS precondition and awaited to a definitive result;
6. only then is the execution marked `SUCCEEDED`.

Discovery, later-page, content, root, audit, processing, timeout, abort, or CAS failure before commit therefore cannot advance the checkpoint. A CAS conflict is surfaced and the run is not recorded as successful. Previous trusted checkpoint state is preserved. The orchestration deadline prevents entering checkpoint commit after expiry. Once a fully valid checkpoint CAS begins, it is no longer raced against that deadline: its bounded database operation is awaited so terminal execution status cannot disagree with committed durability.

Checkpoint organization, source type, connection/source ID, processing version, stable source document identity, fingerprint, provenance, and optional cursor are generated by the existing incremental processor. Filenames and paths are not identities. Removal is derived only from a complete authoritative enumeration.

## Deadline and cancellation

The hard orchestration deadline covers listing, metadata/ancestry proof, download, corpus completion, and checkpoint commit. The signal-binding transport propagates the same `AbortSignal` to each underlying Drive transport request. The bounded HTTP transport links that signal to its request controller. A late completion observes the aborted signal before checkpoint save and cannot produce terminal success.

## Callback fixed identity

The framework-neutral Cloud Run callback handler accepts GET on one configured exact path and consumes only `state`, `nonce`, `code`, or OAuth `error`. Duplicate protocol parameters are rejected. Headers, cookies, body, and extra query identity fields are ignored. Responses are JSON with `Cache-Control: no-store` and never echo protocol values, secrets, or stack traces.

`FixedIdentityDurableCallbackAdapter` closes over server-configured organization, operator, connection, and callback URL and invokes the existing `DurableGoogleDriveCallbackRuntime`. The runtime retains READY preflight, one-time durable state consumption, OAuth exchange, KMS-backed vault persistence, and lifecycle transition. Browser input cannot select tenant, operator, connection, callback URL, root, or source.

## Composition and configuration

`composeRealGoogleDrivePilot` is the explicit composition boundary. It accepts raw audited dependencies and constructs the `RealGoogleDriveClient`, signal binding, real driver, and orchestrator itself. One validated activation configuration determines organization, connection, authorized root, callback identity/path, checkpoint source identity, and limits. Organization, connection, or root mismatch fails before any request; a checkpoint with a different organization/source identity is rejected before orchestration. Importing the module performs no I/O and constructs no live adapter.

`parseRealPilotCompositionConfiguration` centralizes activation configuration and additionally requires a nonempty operator ID, an absolute query/fragment-free callback path, a concrete Secret Manager version reference, and a concrete KMS crypto-key version resource. The existing activation parser validates organization, connection, authorized root, exact HTTPS callback URL, OAuth client ID, readonly scope, explicit activation/persistence gates, and bounded pilot limits. There is no all-Drive or cross-tenant fallback.

## Offline rehearsal

The production-shaped offline test uses the real client, real driver, real orchestrator, real incremental processor, deterministic understanding provider, in-memory lifecycle/execution/checkpoint ports, and an injected zero-network Drive transport.

Run 1 processes 40 synthetic PDFs and commits checkpoint version 1: 40 discovered, 40 understood, 0 reused. Run 2 keeps 38 records reusable, changes one document, renames one without changing its source identity, introduces one new source ID with duplicate bytes, and authoritatively removes one prior ID: 40 discovered, 2 understood, 38 reused; checkpoint advances to version 2. Provider batch document counts are `[40, 2]`.

Focused failures cover retryable and terminal transport errors, post-discovery move outside root, audit unavailability, processing failure, and checkpoint CAS conflict. Existing B2-B1 tests retain later-page failure, hard timeout/non-cooperative download, lifecycle/preflight, persistent audit, and durable callback behavior. In every tested incomplete path, checkpoint state remains at the prior trusted version.
